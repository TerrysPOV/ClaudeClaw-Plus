## Architecture decisions (frozen)

Decisions not to be re-litigated, each with its rationale.

1. **PTY turn evidence comes from the session transcript, never the screen.** The screen is never evidence that a prompt was accepted, that a turn finished, or of what the answer was. Only the session transcript is. The screen may be used for readiness, dialogs and liveness, and only to stop or fail a turn, never to mark it successful.
   Rationale: #559 and the #562 soak showed repaints, chunk splits, prompt echo and CLI chrome changes each producing a false success; the transcript-reading bus path went 99/99. Enforced by `src/__tests__/pty-turn-evidence-guard.test.ts`, which follows the module graph (round 3). A turn's outcome has three states from the transcript alone: running, finished OK, finished FAILED (API error, command stderr, uncertain attribution); the outcome is committed when the transcript establishes it and the screen only delays the return. "Established" means the transcript shows an authoritative boundary after the final message: the CLI's `turn_duration` record, or the next real user prompt (round 5). Nothing else ends a turn: not a quiet file (no inactivity timer) and not a progress, hook, attachment or other bookkeeping record, which neither close nor cut the final message (later lines of the same message id still extend the answer). Error records are read first: an API error anywhere before the boundary fails the turn. With no boundary by the turn's timeout the turn is UNCERTAIN (`PtyTranscriptUncertainError`): no answer, no replay. The answer is the FINAL assistant message by identity (message id), whether or not it has text: a textless final message is `empty reply in transcript`, never the narration before it (round 6). Error flags are read first on every assistant record whatever its shape. An id-less assistant line beside any other assistant line of the turn fails as uncertain (`ambiguous`). Assistant lines of different messages that interleave (A, B, A: a message begins, another runs, the first goes on; every line counts, ignored ones too) fail as uncertain (`ambiguous`, `INTERLEAVED_TEXT`): the final message is the one carrying the first terminal stop reason with all its blocks joined by id, and a turn whose lines cannot be placed in one reply names none (round 7). A reply with no text is a failure (`empty reply in transcript`), on every caller; `/compact`'s own output is exempt. (Operator ruling, Terry, 2026-10-21; boundary rule, kill-and-resume and empty = failure, Terry, 2026-10-22.)

2. **A turn that is not a proven OK kills the process and resumes the session.** Whenever a turn ends in anything but a proven OK (uncertain, prompt not accepted, ambiguous, transcript timeout, API error, replaced transcript, empty reply, a process that closed after the prompt went out), the supervisor retires the entry: it disposes the process, waits for the OS to confirm it has exited, and only then returns the error. "Confirm" is a pid probe (`process.kill(pid, 0)`: ESRCH is gone, EPERM is alive), not bun-pty's exit event: bun-pty 0.4.9 `kill()` ignores its signal, fires that event at once and makes later calls no-ops, so the event proves nothing. After a 2 s grace `dispose()` sends SIGKILL itself, to the process group (the child is its own group leader, so its MCP children go too) and to the pid, and at 7 s it rejects with `PtyExitUnconfirmedError`. The supervisor then quarantines the SESSION (round 7 keyed it; round 8 keys it by supervisor key AND claude session id, in `pty-quarantine.ts`, independent of whether an entry is still tracked). One gate, `assertSessionWritable`, is passed by every path that can start a claude on a session: PTY spawn, respawn and admission (`PtyQuarantinedError`), `sendToLiveSession` (checked first and again under the lock; answers `failed`, never `not-live`), the one-shot fallback in `live-session-actions.ts` (both `not-live` and `skipLive`), `runOneShot` with `resumeSessionId`, the legacy `claude -p --resume` and the bus session manager. The gate retries the confirmation, so the next use from any path releases a quarantine once the pid is gone; `retirePtySession` rejects when the exit is unconfirmed. Round 9: a retirement fences its session from its first synchronous step (the fence becomes the quarantine record when the exit is unconfirmed, and is lifted when it is confirmed), a synchronous `assertSessionSpawnable` runs on the line immediately before every process creation, after all async preparation, and the gate honours the caller's deadline and abort signal (the confirmation goes on in the background and the quarantine is kept, never released on a timeout). Signals are identity-checked: the child's start time is recorded at spawn and compared before every signal, a gone pid or a changed identity means the original exited, and with no identity recorded only the initial retirement may signal. Quarantined sessions are listed by `snapshotSupervisor()` (key, pid, reason, since); `/kill` and shutdown report how many exits stayed unconfirmed. On win32, where there is no pid probe, retirement still waits for the exit event. No retry, no replay (a timeout is exit 124). The next call spawns a new process that `--resume`s the SAME session id, and not before the old one has exited. Only a process that was already gone before the prompt was written is retried. Cron does not retry an uncertain or timed-out PTY turn either (round 9 add-on, Terry, 2026-10-22): the supervisor marks such a result with `failureKind` (`uncertain` or `timeout`), `RunResult` carries it, and `job-loop.ts` skips the job's `retry` for it, because the turn may have completed and a retry can repeat its side effects; a definite failure (prompt never sent, empty reply, API error record, spawn failure, quarantine refusal) still retries as configured. #562 final round (#592): a retirement holds the session, by key, from its first step until every spawn or respawn still pending on the entry has settled and the process it produced is confirmed dead (past a 15 s bound the session is quarantined, never released).
   Rationale: the only writer that could append a late record for the failed turn is dead before any later turn marks its offset, so the transcript's exact payload match is safe without per-submission ids and the transcript reader keeps no memory of failed submissions (the round-4 "unresolved" registry, with its TTL and eviction, is gone). Pattern from ClaudeClaw-Ultra's PTY supervisor. Where it lives: `retireEntry` in `src/runner/pty-supervisor.ts`.
