# Interactive one-shot isolation (#570)

Status: **green on Claude Code 2.1.304, and only from that version up: `pty` starts with `caps.isolation: false` and the startup version probe turns it on (r9).** Untrusted
one-shot routes (`discord.classifier`, `tuner.*`; `memory.recall` never reaches `runOneShot`, see #545) default to the `pty` engine
when `pty.enabled` is true and the detected claude is at least 2.1.304, and to `print` otherwise. HTTP engines remain an explicit opt-in.
One known caveat is recorded under "Intermittent no-reply".

The full run-by-run history (seven workflow runs, the startup rejection, the fixture and readiness
fixes) is in `.planning/570-untrusted-pty/REPORT.md`. This page is the result.

## What was measured

An opt-in integration suite (`tests/integration/untrusted-pty-isolation.test.ts`) drives the real
`runOnceOnPty` untrusted path against the installed `claude` on a disposable GitHub Actions runner,
via `.github/workflows/integration.yml`. It is skipped unless `CI=true`, `GITHUB_ACTIONS=true` and
`RUNNER_TEMP` are set, so it can never plant canaries in a developer's real `~/.claude`. Canaries
live in a throwaway `HOME` and `CLAUDE_CONFIG_DIR`. No credential is printed.

Every row has two directions. The control is present and the canary must stay silent. Then the
control is removed and the same canary must fire (a "twin"). A row whose twin cannot go red proves
nothing, and the suite fails it.

**Positive control.** One spawn with no isolation flags at all (`--model haiku` only), same planted
config. All three discoverable canaries fired: the MCP stub started, the hook marker was written, and
the memory passphrase appeared in the assistant transcript. Without this, "canary absent" would be
unfalsifiable.

| Property | Production control | Control present | Control removed (twin) |
| --- | --- | --- | --- |
| Tools refused | `--tools ""` | no marker, no `tool_use` | marker created or `tool_use` seen: RED |
| MCP absent | `--strict-mcp-config` (and no config supplied) | stub never started | stub started: RED (whole argv policy removed, see note) |
| Settings and hooks | `--setting-sources ""` | no hook marker | hook marker written: RED |
| User memory | `--setting-sources ""`, empty cwd | passphrase absent from reply | passphrase present: RED (whole argv policy removed) |
| Slash commands | `--disable-slash-commands` (flag alone, input guard bypassed in the test only) | command canary absent | canary present: RED |
| Transcript | cleanup in `runOnceOnPty`'s `finally` | a real JSONL existed during the turn, none after | JSONL left behind: RED |
| Environment | caller's print env policy | fake secret absent from `/proc/<pid>/environ` | fake secret admitted: present: RED |

Note on MCP and memory twins: discovery of user-scope MCP servers and `CLAUDE.md` overlaps the
source-restriction, tools and strict-MCP controls, so those two twins remove the entire isolation
argv. They show the fixture is live and that the combined policy is what silences it. They do not
attribute the effect to a single flag.

The slash-command row isolates the CLI flag from the production input sanitizer. A test-only seam
(`setPromptPrepareForTests` in `src/runner/pty-process-test-seams.ts`, a callback never reachable from settings or
`OneShotRequest`) writes the command past the sanitizer. In production the sanitizer is a second guard.

## Shared argv

`UNTRUSTED_CLAUDE_ARGS` in `src/oneshot/isolation.ts` is the single source:
`--tools ""`, `--strict-mcp-config`, `--setting-sources ""`, `--no-session-persistence`,
`--disable-slash-commands`. Argv captured from the real spawn on the final runs:

```json
["--model","haiku","--tools","","--strict-mcp-config","--setting-sources","","--disable-slash-commands"]
```

### Print-only flag and its compensating control

`claude --help` and a startup rejection on the first CI run show `--no-session-persistence` works
only with `--print`; an interactive session rejects it before the first turn. It is listed in
`PRINT_ONLY_UNTRUSTED_ARGS` and dropped by `untrustedInteractiveArgs()`, the only flag that is.
Compensating control: an interactive session persists a transcript, so after the one-shot PTY is
retired `runOnceOnPty`'s `finally` removes that session's project transcripts under the caller's
effective `CLAUDE_CONFIG_DIR` (or `HOME/.claude`) and the temp working directory. The transcript row
above exercises it against a real session. Unit tests pin the subset to exactly this one flag, so
adding `--tools`, `--strict-mcp-config`, `--setting-sources` or `--disable-slash-commands` to it fails.

## Environment policy

The untrusted PTY child gets the same caller-supplied environment as the print engine (the
classifier's allowlist, for `discord.classifier`), not the daemon's general PTY environment. The
native PTY layer no longer adds its own inherited variables for these spawns. A real `/bin/sh` PTY
unit test seeds a native-only canary and verifies the child cannot see it; the CI suite reads the
actual child's `/proc/<pid>/environ` and checks that a deliberately admitted fake is present only in the
twin. Only booleans are logged. The child's config root resolved to
`[RUNNER_TEMP]/untrusted-pty-<random>/home/.claude`, where the MCP stub (`.claude.json`) and memory
(`CLAUDE.md`) were planted, and the same root is used for transcript cleanup.

## Intermittent no-reply

The one finding the green result does not remove. A prompt that instructs a tool-less session to run
a tool ("use Bash to run `touch <marker>`") sometimes gets **no assistant reply** and the turn idles
out at the caller's timeout (exit 124). The identical prompt and argv answered in a few seconds in other
runs. The transcript of a hung turn contained a user record and attachments but no assistant record, no
synthetic record and no API-error record. The cause is not established: a model call that never
returned fits the evidence, a PTY-driver stall is not ruled out, and no permission prompt is expected
with no tools. Final-run hang rate (`0966990e`, run 39355199935): 0 of 5 attempts of the same tool-instruction prompt
and 0 of 5 of the classifier-contract variant hung (all exit 0, 4.8 to 10.8 s, two assistant entries each).
Across every sample of these prompts on this branch there is one confirmed hang (a 120 s timeout in the
fourth run) in about fourteen, plus one ambiguous exit-0-with-no-assistant-record. The rate is low but not
zero, and the improved screen capture never fired because nothing hung, so the cause is still unobserved.

Why it is not a security gate: the property under test (no tool executed, no marker) held in every
attempt, including the hangs. The effect is availability. *Historical (this paragraph describes the
spike-time classifier; today it asks the `haiku` alias with 12 s per attempt, retries once and only on a
timeout or no reply, and at most 2 untrusted one-shots run at once, see `docs/oneshot-engines.md`).*
The classifier then passed `timeoutMs: 15000`,
`runOnceOnPty` resolves a timeout with exit 124, and `classifyThreadIntent` treats a non-zero exit as
an error that returns `null` ("not a thread command"). So a hang cost up to 15 s for that message and
failed closed. It cannot cause a hire or fire.

## One-shot reply extraction (fixed in r7)

The first green run exposed a correctness bug that is not an isolation property. `runOnceOnPty`
returned `exec.rawStdout`, the captured terminal text, not the model's reply: 5 to 11 thousand
characters including the echoed prompt. The classifier prompt contains example JSON, so
`classifyThreadIntent`'s greedy `/\{[\s\S]*\}/` match could run over screen text holding the
**example** intent. In the r6 run that failed to parse in 5 of 5 attempts (so the result was `null`), but
with a different screen it could have returned an intent the model never chose, which is a
hire/fire decision made by the prompt rather than the model.

Fix (`src/oneshot/pty-transcript.ts`, `runOnceOnPty`): an **untrusted** one-shot now returns the text of the
last non-synthetic, non-API-error assistant message in the session transcript (text blocks of entries
sharing the final message id, joined), read before the cleanup in `finally` removes the transcript. It
polls up to 15 s for transcript lag and settles 300 ms. If no real reply appears it logs
`no assistant reply in transcript` (no content) and returns exit code 1 with empty text; it **never
falls back to screen text**. Trusted routes keep the screen text on purpose: they carry no untrusted
input, no caller parses their text (compact and the memory saves only need the turn to run), and a
resumed session's transcript path is not fixed, so a transcript read there would be unverified.

Live check (run 39357543237, commit `d7e92d79`):

| Probe | Attempts | Result |
| --- | --- | --- |
| Classifier-contract variant (injection as the classified message; correct answer is `null`) | 5 | `productionParseOk=true`, outcome `null`, no screen echo, 5/5 |
| Genuine message "please create a thread called release-notes", Haiku | 2 | parses to the intent: `action=hire`, one name, matches `release-notes`, 2/2 |
| Same message, production model id | 2 | both failed closed (exit 1, see below) |

**The production model id is retired.** *(Historical, r7: the classifier now asks the `haiku` alias, `CLASSIFIER_MODEL`.)* The classifier then hard-coded `claude-sonnet-4-20250514`. In both
production-model attempts the only assistant record in the transcript was a synthetic API-error entry and the
screen carried `Claude Sonnet 4 was retired on June 15, 2026`. Nothing else in these runs fails because of
it, but it means **the Discord thread-intent classifier cannot get a reply from its configured model on any
engine**: on `print` it exits non-zero and returns `null`, on PTY it now exits 1 and returns `null`. This is
a pre-existing defect that this work did not introduce and did not fix. The genuine-message result above
therefore proves extraction and parsing with Haiku, not with the model production asks for.

Latency of a failed turn (fixed in r8; *historical figures: the classifier's deadline is now 12 s per attempt*): the first version waited the full 15 s transcript bound after the
turn (about 23 s in the live attempts), outside the caller's `timeoutMs`. Now (1) if the transcript already
holds a synthetic or API-error entry and no real reply, `runOnceOnPty` returns exit 1 at once, and (2) the
transcript wait is what the turn left of `timeoutMs`, capped at 15 s, with a 1 s floor, so it counts against the
caller's deadline. Live (run 39359586393, `fc9d830d`): the retired production model id returned exit 1 in
**3.6 s** with a warning naming `api-error`, well inside the classifier's 15 s deadline. One consequence: an
API-error entry followed later by a real reply in the same turn is not waited for. The CLI writes that entry
only after its own retries, so this is expected to be rare, and the failure is closed (`null`).

## r9: what the first review found, and what the live runs measured

The r1 to r8 evidence **pre-seeded the trust entry** for the throwaway cwd in the test harness
(`projects[<cwd>].hasTrustDialogAccepted`), while production deliberately skips the supervisor's trust
self-heal for an untrusted spawn. So CI never exercised the real startup. r9 removed the pre-seed. Two live
runs (39364441123 on `a37e7165`, 39365573022 on `645e6525`, Claude 2.1.304) follow.

**Trust (B1).** Every untrusted call runs in a fresh `mkdtemp` cwd, so claude would show "trust this
folder?" with "No, exit" preselected, and the call would stall to its timeout. `runOnceOnPty` now marks the
temp cwd (as given and as resolved) trusted in the **child's** config root (`CLAUDE_CONFIG_DIR`, else `HOME`;
not `homedir()`) through `ensureTrustAccepted`'s locked read-modify-write, and removes the entry afterwards
under the same queue, so `~/.claude.json` does not grow per message (#304). Live: with the harness no longer
pre-trusting, the positive control and every old row still pass in both directions, and the B1 row shows
`trustAtSpawn=true; entryAfterCall=false` with the turn complete. Twin (trust write disabled): no entry at
spawn, no turn (`exit=1`, no assistant record), RED.

**Environment (B2).** The untrusted policy env (print's caller env, which the classifier builds with
`ANTHROPIC_*`, `CLAUDE_*`, `AWS_*` admitted) bypassed the spawn strip list. Interactive claude with
`ANTHROPIC_API_KEY` stops at its "custom API key" gate. The strip list now applies to that env for PTY spawns
(a long-lived `sk-ant-oat01-` token is kept). Live: a fake key in the caller env, baseline: not in the child's
`/proc/<pid>/environ`, turn completes (`exit=0`). Twin (key re-admitted at the spawn boundary): in the env, the
turn does not complete (`exit=124`, no assistant record), RED.

**`@` file mentions (B3).** The REPL expands `@path` anywhere in a prompt, itself and not through a tool call,
so `--tools ""` does not stop it. For untrusted prompts every `@` is replaced by U+FF20 after sanitising.
Live, PTY: baseline canary absent from the reply and the transcript (run 1); twin (replacement off through its
seam) canary present in both: expansion is real and the replacement is what stops it. **`claude -p` expands
it too**: the print engine, unchanged, returned the file's contents (`canaryInReply=true`). So print's
untrusted prompts now get the same replacement through the same helper. Live (run 2): print baseline
`canaryInReply=false`, twin `canaryInReply=true`. The PTY baseline row did not complete in run 2 (see "Live
limits" below).

**Persistence beyond the transcript (C1).** Snapshot of the whole child config root around one untrusted turn
whose prompt carried a canary (path shapes only). New or changed during the turn: `.claude.json`,
`backups/.claude.json.backup.<n>`, `cache/changelog.md`, `history.jsonl`, `plugins/` (the marketplace clone,
804 files), `policy-limits.json` and its stamp, `remote-settings.json` and its synced-at file,
`projects/<encoded cwd>/` (the transcript and a `memory/` directory) and `sessions/<pid>.json` plus
`sessions/<pid>.<hash>.key`. **Two places held the prompt text: `history.jsonl` (one line, keyed by `project`
and `sessionId`) and the project transcript.** `runOnceOnPty` now removes the transcript directory, the
`history.jsonl` lines for this cwd or session, and per-session files by id (`session-env`, `file-history`,
`debug`, `todos`, `sessions/*.json`). After cleanup no file under the config root contains the canary; with
the three removals disabled (twin) the history line and the transcript remain, RED. `sessions/<pid>.*` is
removed by claude itself on exit (it is absent after the call even with cleanup disabled). Left behind and not
prompt-bearing: the `.claude.json` backup (it carries the temp cwd path, not prompt text, and claude writes one
per launch whatever we do), `cache/`, `policy-limits`, `remote-settings`, the plugin marketplace clone, and an
empty `sessions/` directory.

**Locks.** The only lock name seen at top level was `.claude.json.lock`. A `history.jsonl.lock` was never seen
(a mkdir lock is held for milliseconds and the probe polled every 20 ms), so the lock claude uses for
`history.jsonl` is **not established**. The rewrite takes a `mkdir history.jsonl.lock` lock (proper-lockfile's
convention), waits at most 3 s, takes over a lock older than 10 s, and fails closed otherwise. A concurrent claude
appending between our read and rename is bounded by that lock only if claude honours the same convention.
Separately, `.claude.json` is also claude's own read-modify-write file under `.claude.json.lock`; the trust
write and removal (this PR's and #566's) serialise in-process only. Taking claude's lock there is a follow-up.

**Version gate (C2).** Isolation was measured on 2.1.304 only. `caps.isolation` now starts `false` and
`applyPtyIsolationVersionGate` (called from `start.ts` after `claude --version`) sets it only for a build at
least 2.1.304; below that, or when the version cannot be read, untrusted routes resolve to `print` with one
startup warning. A process that never probes (a CLI tool, a test) therefore stays on print. The nightly
workflow runs these rows on the latest claude, which catches regressions upward.

**Smaller fixes.** A late-landing spawn or admission after the call's deadline now triggers a second
cleanup once it has been retired (`lateRetire`). Abort, or the caller's deadline running out, during the
transcript wait returns exit 124. An empty `CLAUDE_CONFIG_DIR` counts as unset and a relative config root fails
closed before the spawn. `req.system` reaches the untrusted PTY as `--system-prompt`, as print passes it. A real
reply followed by an API-error record in the same turn is now a failure (exit 1), not a success. Cleanup
failure stays fail-closed, a deliberate divergence from #554's best-effort rule (prompt text left on disk
outweighs one lost classifier reply); it is logged by step and error code, never content.

**Live limits.** In run 2 the tools baseline and the B3 PTY baseline stopped at the harness's exit-0 guard: the
model tried a tool under `--tools ""`, the CLI wrote a synthetic API-error record after its reply, and the
stricter rule above made that exit 1. In the tools row the transcript held no `tool_use` block (`toolUse=false`); the marker check never ran because the guard stopped the row first. The guard was
widened for those two rows afterwards and **that edit is not live-verified** (no runs left). The tools-baseline
prompt now ends on an API error in about 1 of 5 attempts (hang-rate probe, run 2: `hung=1/5`, an exit 1 with two
assistant entries), up from 0 of 5 in r6 to r8, which is the same intermittent behaviour, now reported as exit 1.

## r11: a throwaway config root for every untrusted call

r9 cleaned up after each call inside the operator's real Claude config root (`~/.claude`,
`~/.claude.json`). Four reviewers (Codex, Opus security, Opus silent-failure, Sonnet test-quality) found the
same weakness from different sides: every one of those cleanups is fragile. The paste cache leaked, the trust
write and removal lost updates to `.claude.json` (no cross-process lock), the `history.jsonl` rewrite could lose a
line (the lock claude uses was never established, and a symlinked history file got the wrong lock), a throw in
session discovery skipped every other step, and nothing retried a cleanup after a crash. r11 removes the cause:
**an untrusted PTY call no longer writes anything about the call under the operator's config root.** (r12 narrows this to what is true: the one write outside the throwaway root is claude's own credential refresh, below.)

**How.** Each call creates `claudeclaw-oneshot-cfg-*` in the tmpdir (mode 0700, a sibling of the temp cwd) with a
minimal `.claude.json` (`hasCompletedOnboarding`, `theme`, `numStartups`, and `projects[<cwd>]` plus
`projects[<realpath cwd>]` with `hasTrustDialogAccepted: true`), and spawns claude with
`CLAUDE_CONFIG_DIR=<that root>`, `CLAUDE_SECURESTORAGE_CONFIG_DIR=<operator config dir>` (or `""` when the operator
has none; an empty `CLAUDE_CONFIG_DIR` counts as unset) and `HOME` unchanged. The root is removed in the call's
`finally` and again after a late spawn settles. No credential is copied.

**Why `CLAUDE_SECURESTORAGE_CONFIG_DIR` keeps the login.** Read out of the claude 2.1.304 binary
(`~/.local/share/claude/versions/2.1.304`; identifiers are minified, the shape is verbatim):

```js

function uB(e=""){let n=process.env.CLAUDE_SECURESTORAGE_CONFIG_DIR,t=n!==void 0?!n:!process.env.CLAUDE_CONFIG_DIR,r=n!==void 0?n.normalize("NFC"):Me(),a=t?"":`-${c("sha256").update(r).digest("hex").substring(0,8)}`;return`Claude Code${cn().OAUTH_FILE_SUFFIX}${e}${a}`}
function h(){let e=yD(),r=".credentials.json";return{storageDir:e,storagePath:oe(e,".credentials.json")}}
```

`yD()` is the credential directory: the variable when it is defined at all (so `""` is defined and means
`~/.claude`), else the normal config directory `Me()`. `uB()` is the macOS keychain service name: the suffix is empty
when the variable is `""`, or when it is undefined and `CLAUDE_CONFIG_DIR` is empty or unset; otherwise it is
`-` plus the first 8 hex characters of the SHA-256 of the NFC-normalised directory. `h()` is the Linux plaintext
store: `<yD()>/.credentials.json`. So pointing `CLAUDE_SECURESTORAGE_CONFIG_DIR` at the operator's own directory (or
`""`) makes the child read the operator's login, while `CLAUDE_CONFIG_DIR` points everything else at the throwaway.

**r12: the one write outside the root, and its lock.** `CLAUDE_SECURESTORAGE_CONFIG_DIR` also selects where a refreshed
OAuth token is written. That is claude's own refresh of the operator's own token and carries no prompt data; it is accepted.
Read out of the 2.1.304 binary (`~/.local/share/claude/versions/2.1.304`, byte offsets 218117501 and 218121010; identifiers
are minified, the shape is verbatim), the refresh lock is keyed by the secure-storage directory, not by `CLAUDE_CONFIG_DIR`:


So a one-shot and the daemon's own claude contend on `<credential dir>/.oauth_refresh.lock` whenever they resolve the same
credential directory, which is the case here: the one-shot gets the operator's `CLAUDE_CONFIG_DIR` (or `""` for
`~/.claude`) as `CLAUDE_SECURESTORAGE_CONFIG_DIR`, and the daemon's claude, with the variable unset, resolves `Me()`, the
same directory. The lock is **not** under the throwaway `CLAUDE_CONFIG_DIR`, so the stop condition (a one-shot and the
daemon refreshing without a shared lock) does not apply. Not measured: an actual refresh (see the r12 section of the
report).

**macOS is not measured.** CI is Linux. For the keychain this reading shows only the suffix rule above; it does
not show the base service name (`OAUTH_FILE_SUFFIX` and the argument to `uB` were not read), and it does not show
what `Me()` returns for an operator whose `CLAUDE_CONFIG_DIR` has a trailing slash or a symlink (we pass the raw
string, claude hashes what it resolves). The common case (no `CLAUDE_CONFIG_DIR`, so `""` and no suffix) matches
the unsuffixed service claude itself uses. Nothing here has run against a keychain.

**Deleted.** The trust write and removal for untrusted calls (`pty-trust-prompt.ts` is back to its pre-r9 form),
the `history.jsonl` rewrite with its mkdir lock and `Atomics.wait`, the `sessions/`, `todos/`, `file-history/` and
`debug/` per-id deletions, `untrustedSessionIds`. Nothing on the untrusted path writes under the operator's root;
`src/oneshot/pty-untrusted-state.test.ts` snapshots (path, size, sha256) the operator's root and `HOME` around a
successful and a failed call and requires them identical.

**Fail closed.** If the root cannot be created or seeded, the call fails before the spawn (exit 1, nothing left). If it
cannot be removed, the error is logged by step and code and the call throws, as D6 did. **Startup sweep.** A daemon
start removes `claudeclaw-oneshot-cfg-*` and `claudeclaw-oneshot-pty-*` directories older than ten minutes, and the
sweep runs again every ten minutes after that, which replaces the missing retry.

**Other r11 changes.** Settings load no longer depends on the startup probe (an explicit `pty` untrusted route loads;
the call refuses it while isolation is off, with the version in the message). The reply of every untrusted print or
pty call gets U+FF20 mapped back to `@`, in `registry.ts`. An untrusted PTY traces metadata only under
`CLAUDECLAW_PTY_DUMP`.
